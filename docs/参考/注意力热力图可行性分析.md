## 0. 结论速览（先看这 8 条）

1. **可行，而且不需要任何三方库。** 全部视觉要素都能用 ArkUI 原生能力 1:1 复刻，
   没有任何一项需要 WebView、ECharts 或自研渲染引擎。
2. **三方库里没有现成能用的热力图组件。** 三层证据（详见 §4）：
   ① 本工程已在用的 `@ohos/mpchart@3.0.30` 一共导出 **15 种图表**
   （Bar / CandleStick / Line / Radar / HorizontalBar / Bubble / Pie / Rose /
   Scatter / Combined / Waterfall / Gauge / Area / Funnel / WordCloud），
   **独独没有 HeatmapChart** —— 这是**直接读本地安装包 `index.ets` 源码**得到的结论，不是搜索来的；
   ② ohpm 中心仓用 20+ 关键词系统检索，**零个矩阵热力图包**
   （唯一命中 `heat` 的 `@ohmos/activity_overview` 是 GitHub 日历贡献格子，不可用）；
   ③ `OpenHarmony-TPC/tpc_resource` 权威资源汇总里**零热力图条目**。
   > 配套调研全文：`docs/参考/鸿蒙热力图三方库调研.md`
3. **鸿蒙端可以比 Web 端实现得更简洁。** Web 端"离屏 canvas 画网格 → `globalAlpha=0.4` 贴回"
   这一整套，在鸿蒙上可以用「16×16 的 `PixelMap` + `<Image>` 放大 + `.opacity(0.32)`」一行搞定，
   **并且不需要手动 base64 解码**（`<Image>` 原生支持 `data:image/jpeg;base64,...`）。
4. **推荐路线（路径 A）已经写出可编译、零告警的原型**，并且已确认进入编译产物：
   `harmony/entry/src/main/ets/components/charts/AttentionHeatmap.ets`。
5. **⚠️ 本项目有一个会让"验证"彻底失效的坑：未被引用的 `.ets` 根本不进编译器。**
   我做了对照实验：往 `components/` 下放一个类型错误的文件，`BUILD SUCCESSFUL` 照样通过；
   把它挂到入口页后，立刻编译失败并精确报出 `文件:行:列`。详见 §2.2 —— **这决定了下一个会话必须怎么验证**。
6. 因此本轮额外建了一个**独立探测页** `pages/HeatmapProbePage.ets`（已注册进 `main_pages.json`），
   它既是"能编译"的证据，也是真机上目视验收的入口。**验证完可直接删除。**
7. 性能不是问题：服务端推帧间隔是 `asyncio.sleep(0.2)` ≈ **5fps**（`services/frame_processor.py:139`），
   单帧热力图只有 16×16=256 个采样点。
8. 需要为下一个会话预留的唯一"降级开关"是 **`roundRect` 是 API 20+ 的 API**，
   若将来把 `compatibleSdkVersion` 降到 18 及以下需要走 `arcTo` 手写圆角 —— 原型里**两条路径都已实现**。

## 1. 需求还原：Web 端这个组件到底做了什么

### 1.1 视觉要素（6 项，一项都不能少）

来源：`FacePreview.vue` 的 `template` + `drawFace()` / `drawHeatmap()` / `drawRegionBoxes()`。

| # | 要素 | Web 实现细节 | 关键数值 |
|---|---|---|---|
| ① | **对齐人脸底图** | `new Image()` + `data:image/png;base64,...` → `ctx.drawImage(img, 0, 0, 200, 200)` | 画布 **200×200**，原图 128×128，拉伸铺满 |
| ② | **16×16 热力网格** | 离屏 canvas 上 `fillRect` 256 次，每格 `fillStyle = heatColor(v)` | 每格 **12.5×12.5** |
| ③ | **叠加合成** | `ctx.globalAlpha = 0.4; ctx.drawImage(offCanvas, 0, 0)` | **等效每像素 alpha = 0.8 × 0.4 = 0.32** |
| ④ | **4 个解剖区域标注** | 虚线圆角矩形 + 文字，坐标基于 canonical 128×128 | `scale = 200/128 = 1.5625`；框 **26×18**，圆角 4，`setLineDash([4,3])` |
| ⑤ | **色带图例** | CSS `linear-gradient(to right, #0000ff, #00ffff, #00ff00, #ffff00, #ff0000)` | 5 段停靠：0 / .25 / .5 / .75 / 1 |
| ⑥ | **占位态** | 8×8 网格底纹 + 居中「等待推理数据...」 | — |

四个标注区域的**原始坐标与颜色**（照搬，不要改）：

| label | cx | cy | color |
|---|---|---|---|
| 眶周 | 38 | 52 | `rgba(0,230,180,0.5)` |
| 眶周 | 90 | 52 | `rgba(0,230,180,0.5)` |
| 口周 | 64 | 92 | `rgba(77,138,240,0.5)` |
| 眉间 | 64 | 36 | `rgba(240,160,40,0.5)` |

### 1.2 色彩映射 `heatColor(t)`（**逐位等价是硬要求**）

```ts
const r = clamp(t < 0.25 ? 0 : t < 0.5 ? (t - 0.25) * 4 : 1)
const g = clamp(t < 0.25 ? t * 4 : t < 0.75 ? 1 : (1 - t) * 4)
const b = clamp(t < 0.5  ? (0.5 - t) * 4 : 0)
return `rgba(${r*255},${g*255},${b*255},0.8)`
```

采样点（原型探测页会把这张表画出来，用于两端肉眼比对）：

| t | 0 | 0.25 | 0.5 | 0.75 | 1.0 |
|---|---|---|---|---|---|
| RGB | `(0,0,255)` 蓝 | `(0,255,255)` 青 | `(255,255,0)` 黄 | `(255,255,0)` 黄 | `(255,0,0)` 红 |

> ⚠️ 注意：0.5 与 0.75 都是黄色，绿色只出现在 (0.25, 0.5) 的过渡带里。**不要"顺手优化"成均匀五段**，否则两端颜色对不上。

### 1.3 Top-3 热点 → 解剖区域（业务语义，必须保真）

`hotspots` computed 的判定顺序与阈值（**顺序即优先级，不能重排**）：

```
1. regionY < 0.3  && 0.3 < regionX < 0.7                          → 眉间/前额区域
2. 0.25 < regionY < 0.45 && (regionX < 0.35 || regionX > 0.65)    → 眶周区域（眼轮匝肌）
3. regionY > 0.5  && 0.3 < regionX < 0.7                          → 口周区域（降口角肌）
4. 0.4 < regionY < 0.55 && 0.35 < regionX < 0.65                  → 鼻唇沟区域
5. 其它                                                            → 面部中央区域
```

文案模板：`重点关注 {区域}（{百分比}%），其次 {区域}（{百分比}%）`，
百分比 = `(v * 100).toFixed(1)`。

### 1.4 数据契约（鸿蒙端已经具备，无需改动网络层）

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `heatmap_data` | `number[][]` | `POST /api/analyze/face` 与 WS 帧 | **16×16**，行优先 `data[y][x]`，值域 [0,1] |
| `aligned_face` | `string` | 同上 | base64，**裸串或带 `data:` 前缀两种都可能** |
| 推帧频率 | — | `frame_processor.py:139` `await asyncio.sleep(0.2)` | 单图路径共 10 帧 ≈ **5fps** |

> ★ 已在鸿蒙侧就位的桥接（**本轮不需要改**）：
> `AppStore.analysisHeatmap(): number[][]`（`store/AppStore.ets:590`）
> `AnalysisStateHolder.alignedFaceDataUrl(): string`（`store/AnalysisStateHolder.ets:87`，**已经自动补 `data:image/jpeg;base64,` 前缀**）
>
> ★ **纠正一处历史文档笔误**：`docs/项目分析报告与HarmonyOS端构建方案.md` 第 722 行说
> `FacePreview.vue` 用 `data:image/png` 前缀是"陷阱"。实际上服务端 `_encode_base64()`
> （`services/frame_processor.py:62-68`）走的是 **PIL `img.save(buf, format="JPEG", quality=75)`**，
> 编出来的确实是 **JPEG**；而鸿蒙侧 `alignedFaceDataUrl()` 写的也是正确的 `image/jpeg`。
> **结论：鸿蒙端不吃这个坑**，Web 端那个 `image/png` 前缀只是浏览器按内容嗅探、将错就错。
> （记录在此仅为解释历史文档为何有此一说，鸿蒙端无需任何兼容处理。）

### 3.3 ArkTS 编译器的硬性约束（实测踩到）

- **`createPixelMapSync` 与 `roundRect` 都被标记为"可能抛异常"**，不写 `try/catch` 会出
  `ArkTS:WARN ... Function may throw exceptions. Special handling is required.`
  原型已按此处理，**当前本工程源码 0 告警**。
- `@ohos.router.back()` 自 **API 18 起废弃**，应改用 `this.getUIContext().getRouter().back()`
  （出处：`api/@ohos.router.d.ts`，`@deprecated since 18 / @useinstead ohos.arkui.UIContext.Router#back`）。
- Canvas 绘制坐标默认单位是 **vp**（不是 px）。若要用 px 需
  `new CanvasRenderingContext2D(settings, LengthMetricsUnit.PX)`，**且配置后无法更改**。

## 4. 三方库调研：有没有现成能直接用的？

### 4.1 `@ohos/mpchart` —— ❌ 没有热力图

**方法：直接读本工程已安装的包源码**（比任何搜索都可靠）：
`harmony/oh_modules/.ohpm/@ohos+mpchart@3.0.30/oh_modules/@ohos/mpchart/index.ets`

导出的组件**共 15 种，逐一列举**：

```
BarChart · CandleStickChart · LineChart · RadarChart · HorizontalBarChart ·
BubbleChart · PieChart · RoseChart · ScatterChart · CombinedChart ·
WaterfallChart · GaugeChart · AreaChart · FunnelChart · WordCloudChart
```

外加按名称全包检索 `Heatmap|HeatMap|heat` → **0 命中**。

> 补充事实：MPAndroidChart（Java 原版）**是有** `HeatmapChart` 的，
> 这个鸿蒙移植版**没有移植过来**。所以"mpchart 有热力图"这个预期是错的。

**交叉印证**（来自配套调研报告 `docs/参考/鸿蒙热力图三方库调研.md`）：
读上游仓库的导出表 `library/index.ets` 与全量 `CHANGELOG`（1.0.0 → 4.0.0-rc.1），
同样**全文不含任何 `heat` 字样**；华为官方优选三方库介绍里也明确写的是
「线形 / 柱状 / 饼状 / 蜡烛 / 气泡 / 雷达 / 瀑布 7 大类」。
出处：<https://gitee.com/openharmony-tpc/ohos_mpchart/raw/master/library/index.ets>、

## 5. 实现路径对比

### 路径 A · Stack 三层叠放 + 16×16 PixelMap 放大（✅ 推荐）

```
Stack
 ├─ Image(faceDataUrl)          ← 底图，base64 直出，objectFit(Fill)
 ├─ Image(heatPixelMap 16×16)   ← 矩阵物化成图，.interpolation(High).opacity(0.32)
 └─ Canvas                      ← 只画 4 个虚线圆角框 + 4 个文字（透明层）
```

- **等价性证明**：Web 端每格 alpha 0.8 × `globalAlpha` 0.4 = **0.32**；16 格互不重叠，
  因此 `.opacity(0.32)` 与"逐格 0.32"在数学上**完全等价**，不会出现边缘叠色。
- ✅ 代码量最小（核心 ~50 行）
- ✅ 不需要 base64 解码（省掉 `Base64Helper` + `createImageSource` 两条链路）
- ✅ 平滑放大是**免费的**（`interpolation(High)`），且天然无接缝
- ✅ 三层解耦，将来加"拖拽/缩放/显隐开关"只动一层
- ⚠️ `Image` 的插值观感需要在真机上与 Web 截图比对（见 §8-R2）

### 路径 B · 单 Canvas 全量绘制（与 Web 结构同构）

```
ctx.drawImage(facePixelMap, 0,0,200,200)
ctx.globalAlpha = 0.4
for 256 格: ctx.fillStyle = heatColor(v); ctx.fillRect(...)
ctx.globalAlpha = 1
+ 标注框 + 色带
```

- ✅ 与 `FacePreview.vue` **结构完全同构**，移植时不用重新设计
- ❌ 必须先 base64 → `createImageSource` → `createPixelMap`（多两条链路、多一次 JPEG 解码）
- ❌ 256 次 `fillRect` 在 **12.5vp** 这种非整数格宽下，抗锯齿会在格子缝处产生可见细线
  （Web 端同样存在，但鸿蒙 vp→物理像素还要再乘 density，缝隙更明显）
- ❌ 底图与热力图层在同一个 Canvas 里，改一处要整体重绘
- 结论：**作为降级备份保留**（已在 `HeatmapFeasibilityProbe.drawFaceOnCanvas` 中实现并编译通过）

### 路径 C · 离屏画布 `OffscreenCanvas` + `transferToImageBitmap`

- ✅ 对应 Web 的 `document.createElement('canvas')`
- ⚠️ 只适合"先离线合成一张完整叠加图再一次性贴上去"的场景，对本需求没有额外收益
- ⚠️ 注意：**`roundRect` 等路径 API 不会跨 canvas 对象生效**（官方文档明确说明）
- 结论：**备而不用**（已实现并编译通过）

### 路径 D · 端侧像素后处理（`getImageData`/`putImageData`）

- 适用场景：将来要在端侧自己做双三次上采样、高斯模糊、阈值化
- 16×16=256 采样点，算力上毫无压力
- 结论：**目前不需要**，但链路已验证可用

### 对比表

| | A（推荐） | B | C | D |
|---|---|---|---|---|
| 代码量 | 最小 | 中 | 中 | 大 |
| 需 base64 解码 | **否** | 是 | 视情况 | 是 |
| 格子接缝 | **无** | 有 | 有 | 无 |
| 平滑放大 | 免费 | 需 `imageSmoothing` | 需 `imageSmoothing` | 自己算 |
| 与 Web 结构同构 | 否 | **是** | 部分 | 否 |
| 扩展性 | **最好** | 差 | 中 | 中 |
| 编译验证 | ✅ 已过 | ✅ 已过 | ✅ 已过 | ✅ 已过 |

| | mpchart（折线/饼图） | 本热力图 |
|---|---|---|

### 6.4 性能预算

| 项 | 量级 | 判断 |
|---|---|---|
| 推帧频率 | ~5fps（`asyncio.sleep(0.2)`） | 宽裕 |
| 每帧新建 PixelMap | 16×16×4 = **1024 字节** | 可忽略（务必 release） |

// ① 矩阵 → PixelMap（唯一的"矩阵变图片"入口）
const bytes: Uint8Array = new Uint8Array(rows * cols * 4);
for (let y = 0; y < rows; y++) {
  for (let x = 0; x < cols; x++) {
    const rgb: number[] = HeatmapUtil.heatRgb(data[y][x]);
    const i: number = (y * cols + x) * 4;
    bytes[i] = rgb[0]; bytes[i+1] = rgb[1]; bytes[i+2] = rgb[2]; bytes[i+3] = 255;
  }
}
const opts: image.InitializationOptions = {
  size: { width: cols, height: rows } as image.Size,
  srcPixelFormat: image.PixelMapFormat.RGBA_8888,
  pixelFormat: image.PixelMapFormat.RGBA_8888,
  alphaType: image.AlphaType.UNPREMUL,
  editable: false
};
this.releaseHeatPixelMap();                       // ★ 先放旧的，防 native 泄漏
try { this.heatPm = image.createPixelMapSync(bytes.buffer as ArrayBuffer, opts); }
catch (err) { /* BusinessError */ }

// ② 三层叠放
Stack() {
  Image(this.faceSrc).width(SIZE).height(SIZE).objectFit(ImageFit.Fill)
  Image(this.heatPm).width(SIZE).height(SIZE).objectFit(ImageFit.Fill)
    .interpolation(this.smooth ? ImageInterpolation.High : ImageInterpolation.None)
    .opacity(0.32)                                 // ★ = 0.8 × 0.4
  Canvas(this.annCtx).width(SIZE).height(SIZE)
    .onReady(() => { this.canvasReady = true; this.drawAnnotations(); })
}
