## 1. 本轮做了什么（与上一轮报告的差异）

上一轮报告给的是**施工图**，本轮按图施工，但有**两处必须偏离**，理由如下。

### 1.1 结构调整：把"一张热力图"抽成可传尺寸的方块

上一轮 `AttentionHeatmap.ets` 里，"矩阵 → PixelMap、三层叠放、标注框"整套逻辑
**硬编码了 200vp**。但本轮要做的横向列表里，每一格只有 72vp —— 尺寸必须可传。

所以拆成两层：

```
AttentionHeatmap          ← "面板"：大图 + 色带 + Top-3 解读（详情页主图 / 探测页用）
  └── HeatmapTile         ← "方块"：尺寸可传（tileSize），自己管自己的 PixelMap
```

- **算法只有一份**：`HeatmapUtil` / `HeatHotspot` 现在住在 `HeatmapTile.ets`，
  `AttentionHeatmap.ets` 用 `export { ... } from './HeatmapTile'` 重新导出，
  所以上一轮探测页 `HeatmapProbePage.ets` 的 import **一行都不用改**。
- **每个方块自己持有并释放 PixelMap**：横向列表里会有几十个方块，
  把 PixelMap 集中放在父组件里，列表重排时极易漏释放（native 内存不归 ArkTS GC 管）。
- **标注字号随尺寸缩放**：`fontPx = max(8, round(9 * scale * 1.4))`，
  200vp 时算出来正好是 14px（与上一轮逐位一致），72vp 时降到 12px 不糊。
  72vp 的缩略方块统一 `showAnnotations: false`（放不下 4 个区域的文字），
  主图仍 `showAnnotations: true`。

### 1.2 ★ 页面契约的例外：分析页必须读 store

上一轮报告建议"给 `AnalysisDetailPageParam` 补 `heatmapData` / `alignedFaceUrl` 两个字段"
（`docs/注意力热力图鸿蒙端可行性分析报告.md` §6.2-②）。**本轮没有这么做，这是刻意的**：

> **逐帧数据必须在帧到达的当下进入 UI，而不是等窗口层来同步参数。**

`syncDetailParam()` 只在**切页签 / 点工作台卡片**这类时机被调用
（`MainPage.ets`：`syncTabParam → syncWorkbenchParam → syncDetailParam`），
WebSocket 帧到达时**不会**触发它。若只靠参数，页面上的热力图会停在
"进入本页时那一帧"，看起来像卡死 —— 本轮验证会直接失败。

所以本页改为：**元信息（素材名/类型/快照分数）仍走参数，逐帧数据只读 store**。
纪律的核心部分保留：本页**只读** store，不调任何写方法，动作仍走注入的回调。
这与 `WorkbenchPage.ets` 当初开这道口子的理由**完全同一条**
（见 `MainPage.ets` 与 `WorkbenchPage.ets` 文件头）。

### 1.3 新增数据链路：逐帧序列缓冲

`AnalysisState` 新增一个 `@Trace frameHistory: AnalysisFrameModel[]`：
每收到一帧就 `concat` 出新数组（**整体替换引用**，保证 V2 的 `@Trace` 一定感知），
上限 `MAX_FRAME_HISTORY = 90`，超出丢最旧的。

- 上限依据：服务端图片路径固定推 **10 帧**（`frame_processor.py` 的 `steps = 10`），
  视频路径按 `total // 60` 采样、24 一组成批 flush，**实测一次视频 96 帧**（§5.2）。
  90 帧 ≈ 0.5–1.3MB（每帧含一张 128×128 JPEG base64，实测 7264B/帧）。
- 数据源是桥接器里**那个数组本身**（`AppStore.analysisFrameHistory()` 返回引用，不拷贝），
  所以页面 `@Computed` 读它就等于订阅了"每帧"。

## 3. 分析页现在的结构

```
分析详情
├─ ① 素材与状态卡          （真实数据：进度、帧数、状态）
├─ ② 辅助评估分数卡        （实时模式取 store，快照模式取参数）
├─ ③ 注意力热力图 ★本轮实装
│    ├─ 主图：HeatmapTile(200~300vp) + 色带 + Top-3 热点解读
│    ├─ 数据来源说明：演示数据 / 已固定第 N 帧 / 跟随最新一帧 / 历史快照
│    └─ 横向逐帧列表（视频切分视图）：每格 = 该帧自己的热力图 + 帧号 + BDI
│         · 点一格 → 主图固定到那一帧（该格描边高亮）
│         · 再点同一格 / 点「回到最新」→ 回到跟随最新帧
├─ ④ 情绪曲线（折线图）     ← 仍是占位（本轮不在范围内）
├─ ⑤ 严重度分布（饼图）     ← 仍是占位
├─ ⑥ 智能解读 / 错误提示 / 取消分析
```

### 3.1 横向逐帧列表为什么是这样

- **横向而不是网格**：视频热力图沿时间有序，横向排开才能一眼看出"热点随时间的漂移"；
  网格折行会切断时间顺序。下一轮做真正的视频切分（自定义区间、导出片段）时，
  只要把"按顺序 ForEach"换成"按切分区间分组"，**方块组件不用改**。
- **渲染上限 24 格**（`MAX_STRIP_TILES`）：这是**渲染上限，不是数据上限**。
  每格要建一个 16×16 PixelMap 加一个透明 Canvas，实测一次性渲染 90+ 格会把
  模拟器的渲染服务压死（黑屏 + `LIFECYCLE_TIMEOUT` 冻结日志）。
  完整逐帧数据仍在 `frameHistory`（上限 90），将来换成懒加载/缩略图即可，**不必改数据层**。
- **只渲染有热度矩阵的帧**：视频路径下 `heatmap_data` 缺失的帧会被 mapper 归一化成空矩阵
  （`normalizeMatrix`），把空矩阵交给方块只会得到灰块，所以先过滤。
- **主图与列表来自同一个返回值**（`HeatmapView`）：否则会出现
  "列表高亮第 7 格、主图画第 12 格"这种错位。
- **没手动选过时必须取最后一格**（不是第 0 格）：列表按时间左旧右新排列，
  用户的心智模型是"最右边是最新"。越界下标也退回最后一格，而不是跳到"很久以前的一帧"。

### 5.4 真实服务端数据的形状（在**本机后端**上实测）

用本机后端跑通一次完整 WS 分析，打印服务端真实回推的内容：

```
[health] 200 {'status': 'ok'}
[auth] 注册成功 · harmony_probe
[upload] media_id=59 name=162b04f5240041aca129dbcba84cfa86.mp4 type=video
[ws] status task=59
[ws] frame   1  id=1  score=26.89 heat=16x16 face_b64=7264B
...
[ws] frame  96  id=73 score=26.89 heat=16x16 face_b64=7264B
[ws] done final_score=26.89
[ws] 共收到 96 帧
[ws] 末帧热度：min=0.0000 max=1.0000 非零格=255/256
[ws] 末帧人脸 base64 前缀：/9j/4AAQSkZJRgABAQAAAQAB…
```

三条结论：
1. **视频一次推 96 帧**（不是 10 帧）—— `MAX_FRAME_HISTORY = 90` 与

## 6. 顺带产出：hdc 驱动模拟器的三个小工具

模拟器验证过程中反复踩到两个坑，所以把可复用的部分固化成脚本（都在 `harmony/scripts/`）：

| 脚本 | 解决什么 |
|---|---|
| `capture.ps1` | `hdc file recv` 的**相对路径不以调用方 cwd 为基准**（实测落到 `E:/Git/...`），必须 `Set-Location` 或给绝对路径 |
| `uidump.ps1` | 屏幕坐标与 `uitest uiInput click` 的坐标系**不 1:1 对应**（模拟器有信箱式缩放），必须从布局 dump 里读**真实 bounds**；同时处理 dump 的编码错位（UTF-8 被按 GBK 读入时需要还原） |
| `tap.ps1` | 把 click / inputText / swipe / fling 四个动作封装成一条命令 |

★ 三个脚本里各有一条**必须保留的注释**：
`uidump.ps1` 不能用 `ConvertFrom-Json`（dump 里有畸形 JSON 片段）、
`tap.ps1` 的函数参数**不能叫 `$args`**（与 PowerShell 自动变量冲突，会导致参数静默丢失）。
这两条都是实测踩出来的。
